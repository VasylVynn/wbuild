# План: чат-первый лендінг — онбординг без реєстрації, акаунт лише перед генерацією

> **Дата:** 2026-08-07. **Статус:** v2 — провалідовано двома агентами
> (UX/UI-спеціаліст + технічний рев'юер), усі must-fix внесені нижче.
> Чекає затвердження власником.
> **Джерело:** рішення власника 2026-08-07 + партнерська вимога 07-29 §5
> («а де чат зразу?» — чат = головний CTA). Узгоджено з чинним флоу:
> анонімний чат і auth-гейт на «Створити сайт» ВЖЕ існують — план переносить
> вхід у чат на лендінг і робить перехід через реєстрацію безшовним.

## 1. Цільовий флоу (як бачить користувач)

```
Лендінг (3minsite.com.ua)
  └─ HERO = живий чат (без реєстрації): «Розкажіть про свою справу…»
       ├─ збирає факти, Instagram-імпорт, фото — все як зараз на /new
       ├─ по зібраному: підсумок «Ось що я знаю про вас: …» (вже існує)
       └─ [Створити сайт] → екран реєстрації (email або Google)
            └─ після реєстрації: автоповернення в чат, генерація стартує САМА
                 └─ прев'ю → «Опублікувати» (безкоштовно) → домен-офер ₴999
```

Правила UX:
- Жодного «почни спочатку»: розмова, факти, фото, IG-дані переживають
  реєстрацію 1:1.
- Кнопка «Створити сайт» з'являється тільки після підсумку (як зараз, A6).
- На екрані реєстрації видно ЧОМУ вона потрібна: «Створимо акаунт, щоб сайт
  був ваш: редагування, заявки в Telegram, керування доменом» + міні-прев'ю
  зібраних даних (назва + місто) — користувач бачить, що нічого не втрачено.
- Реєстрація = 1 екран (email+пароль АБО Google, обидва вже працюють).

## 2. Що вже є (не будуємо повторно)

- Анонімний чат: `startConversation` створює placeholder-тенант + conversation
  без auth (`persist-actions.ts:42`); SSE-агент `/api/onboard` публічний.
- Auth-гейт саме там, де просить власник: `handleCreateSite` →
  `sessionStateAction` → не залогінений → phase "gate" (`OnboardChat.tsx`).
- Відновлення розмови: `loadConversation(convId)` повертає messages + facts +
  media + confirmed (`persist-actions.ts:228`) — зараз викликається тільки з
  localStorage.
- Реєстрація: /login з режимом «Реєстрація», Google OAuth, `?next=` редірект.
- IG-імпорт, фото-вет, генерація, прев'ю — без змін.

## 3. Технічні роботи

### 3.1 Чат на лендінгу (root-хост)

- `app/page.tsx`: hero-секція = `<OnboardChat embedded />` (той самий
  компонент; проп `embedded` — компактний хедер, без повноекранного лейаута).
  Нижче лишаються секції прикладів/FAQ (соціальний доказ під чатом).
- Server actions і `/api/onboard` працюють з root-хоста без змін (один апп;
  middleware пропускає платформні хости, `/api/*` поза matcher'ом).
- Rate limits уже стоять (`conversation_start`, `chat_turn`) — лендінг-трафік
  з реклами не спалить бюджет моделей безконтрольно; ліміти env-тюняться.
- Стара сторінка `app./new` ЛИШАЄТЬСЯ (прямі лінки, повернення після логіну).

### 3.2 Крос-хостовий handoff розмови (ключова діра)

localStorage не перетинає origin (lvh.me ↔ app.lvh.me) → conv id мусить їхати
в URL:

- Гейт-екран: замість лінка `/login?next=/new` → абсолютний URL
  `https://app.<root>/login?next=${encodeURIComponent(`/new?conv=<id>&resume=1`)}`
  (через `rootSiteUrl`-патерн, уже є в lib/config).
- `/new` читає `?conv=` → `loadConversation(conv)` з сервера (пріоритет над
  localStorage), пише його в свій localStorage.
- `?resume=1` + залогінений + confirmed → генерація стартує автоматично
  (без повторного кліку «Створити сайт») — «продовжуємо якраз генерацію».
- Безпека: conv id = UUID-bearer. Обмеження: `loadConversation` уже віддає
  лише state розмови (без чужих сесій); додати перевірку «розмова не
  прив'язана до іншого user» при claim (генерація прив'язує tenant_members —
  там і гейт: якщо conversation.tenant вже має owner ≠ поточний user → відмова).

### 3.3 Реєстрація як продовження, не перешкода

- /login при `?next=/new?conv=…`: дефолтний режим = «Реєстрація» (не «Вхід»),
  бо гейт-аудиторія — нові користувачі; тумблер «Вже маю акаунт» лишається.
- Над формою — контекстний блок: «Сайт для «{назва}» майже готовий. Створіть
  акаунт, щоб зберегти його» (назва з query `?biz=<businessName>` — тільки
  відображення, не джерело даних).
- Після signup з підтвердженням email: лист веде на
  `app./new?conv=…&resume=1` (safeNext уже підтримує відносні шляхи).
  ⚠️ Email-confirmation розриває флоу вкладкою пошти — MVP приймає це;
  опція «вимкнути confirm для нових» — рішення власника окремо (§6).

### 3.4 Лендінг-верстка

- Hero: заголовок-обіцянка (1 рядок) + чат одразу під ним, видимий без скролу
  на мобільному (реклама = мобільний трафік).
- Прибрати дубльовані CTA «Створити сайт» з хедера/hero (вели на app./new) —
  тепер CTA = перше повідомлення в чаті; хедер-CTA скролить до чату.
- Meta Pixel/PostHog уже на лендінгу; додати funnel-події:
  `chat_start` вже пишеться в `startConversation` — сегментувати по
  meta.source = "landing" | "new-page" для порівняння конверсії.

### 3.5 Аналітика флоу (міряти зручність, не вгадувати)

- Нові ui_-події: `ui_gate_shown`, `ui_gate_signup_click`,
  `ui_resume_after_auth` (+ серверний `draft_generated` вже є) —
  воронка «чат → гейт → реєстрація → генерація» видима в PostHog/адмінці.

## 4. Що НЕ робимо (YAGNI)

- Ніякого анонімного «прев'ю до реєстрації» — гейт стоїть ДО генерації
  (рішення власника; токени не витрачаються на незареєстрованих).
- Ніякої міграції БД — conversations/facts_state уже зберігають усе.
- Ніякого перенесення auth на root-домен (cookie-домен .3minsite.com.ua) —
  окрема робота, не потрібна для флоу через URL-handoff.
- app./new не видаляємо.

## 5. Ризики

- **Bearer conv id в URL**: хто має лінк — бачить чернетку розмови. Прийнятно
  для MVP (UUID, без PII крім введеного самим користувачем); згадати в privacy.
- **Email-confirmation** ламає безшовність (вкладка пошти). Мітигація §3.3;
  радикальне рішення — Google-кнопка першою (нуль листів).
- **Лендінг = чат** може знизити SEO-контент головної: лишаємо секції під
  чатом, h1 текстовий.
- Вага OnboardChat на лендінгу (великий клієнтський компонент) — LCP: чат
  рендериться як острів під статичним hero-заголовком; виміряти після.

## 6. Відкриті питання власнику

1. Email-confirmation при signup: лишити (безпечніше, але вкладка пошти
   посеред флоу) чи вимкнути в Supabase для гладкості тесту попиту?
2. Хедер-CTA «Увійти» на лендінгу лишається як є?
3. Чат на лендінгу одразу активний (перше повідомлення бота видно) чи
   «сплячий» до першого кліку (економія перших вражень/трафіку ботів)?

## 7. MUST-FIX з валідації (обов'язкові, вносяться у хвилі нижче)

**Безпека/дані (технічний рев'ю):**
- M1. **Claim-гейт проти захоплення сайту**: `generateDraftAction`
  (`actions.ts:179-185`) вставляє owner-membership БЕЗ перевірки наявного
  власника — другий тримач `?conv=`-лінка стає співвласником. Перед вставкою:
  тенант розмови вже має члена ≠ поточного user → відмова. Гонку двох
  браузерів закрити тим самим гейтом (перший claim перемагає).
- M2. **`emailRedirectTo` у signup** (`login/actions.ts:70` — зараз відсутній,
  поштова гілка ГАРАНТОВАНО губить розмову): лист веде на
  `app./auth/callback?next=<двічі-закодований /new?conv=…&resume=1>`;
  URL додати в Supabase Redirect Allow List.
- M3. **Відносні лінки OnboardChat на root-хості ламаються**
  (`/login`, `/sites`, `/edit/*` → 404 через middleware): усі крос-хостові
  href будувати абсолютно через `publicSiteUrl(app.<root>)` (НЕ rootSiteUrl —
  він для кореня).
- M4. `app/page.tsx` отримує `export const maxDuration = 300` (фото-аналіз і
  далі — реальні model-виклики з лендінгу).
- M5. `startConversation` може повернути null (ліміт) → чат без persistence →
  handoff без conv. Фолбек: гейт без conv-параметра чесно показує «почніть на
  app./new» АБО retry створення розмови перед гейтом.
- M6. localStorage-restore на лендінгу: завершена/чужа стара розмова не має
  відновлюватись у hero (очищення після done — на ОБОХ хостах; на root
  відновлювати тільки незавершені).

**Конверсія (UX-рев'ю):**
- M7. Довіра будується НА ГЕЙТІ, не на /login: гейт-екран несе прев'ю
  зібраного (назва, місто, N фото), три рядки «безкоштовно/без коду/заявки в
  Telegram», **Google-кнопку прямо на гейті** (нуль листів) і «Назад до
  розмови». /login-контекст-блок — додатково.
- M8. Екран «Перевірте пошту» після signup: «Розмова збережена» + кнопка
  «Я підтвердив — продовжити» (ре-чек сесії → resume) + повторна відправка.
- M9. Перше повідомлення бота чесно анонсує гейт: «…в кінці попрошу пошту,
  щоб сайт лишився вашим» — реєстрація перестає бути сюрпризом.
- M10. Мобільний: перший фокус розгортає чат у fullscreen-ОВЕРЛЕЙ на тому ж
  root-хості (жодної навігації — вона вбиває localStorage), sticky-інпут на
  dvh; вкладеного скролу нема.
- M11. Залогінений з існуючим сайтом бачить на лендінгу «Ваш сайт: редагувати
  / заявки», а не «розкажіть про справу»; чат — згорнутий «створити ще один».
- M12. `resume=1` авто-генерація ТІЛЬКИ для same-tab OAuth-повернення;
  після поштової гілки — рекап фактів + одна кнопка (bearer-лінк з листа не
  має сам палити 3 хв токенів; повторний visit з готовим draft → у прев'ю).

**SHOULD-FIX (робимо в тих же хвилях):** авторизація/rate-limit на
`loadConversation` (зараз service-role без перевірок, віддає телефони);
знизити `chat_turn` перед рекламою; `igImportEnabled` проп з root-сторінки;
PKCE-примітка в UX-копію листа («відкрийте в цьому ж браузері» — уже є
патерн у reset); зберегти «безкоштовно/домен 999» під чатом; SSE-помилка не
вивалює fullscreen error поверх лендінга; події `ui_chat_first_message`,
`ui_gate_shown`, `ui_gate_abandoned`, `ui_resume_after_auth`.

## 8а. Аналіз реального чату (2026-08-07, lapusigroom) — Lovable-рівень

Власник прогнав живий діалог. Знахідки, за пріоритетом:

**C1 (P0, БАГ) — повідомлення обрізаються і склеюються.** У транскрипті:
«Логот� номера» (втрачені символи + U+FFFD), «Адресаверджено!» (обрубаний
підсумок склеївся з наступною реплікою), «вжееглянути». Клієнтська SSE-збірка
коректна (split по \n\n, TextDecoder stream:true); дельти сервер шле сирими.
Головний підозрюваний — шлях ЗБЕРЕЖЕННЯ/ВІДНОВЛЕННЯ історії:
`route.ts:96` пише в conversations `stripLoneSurrogates(safeSlice(content,
MAX_MSG_CHARS))` — обрізка довгого підсумку по ліміту + можлива втрата
роздільника між turn-раундами при відновленні `loadConversation`. Робота:
відтворити (довгий підсумок + emoji на межах), полагодити збірку finalText /
persist / restore, тест на цілісність round-trip. Це блокер якості ДО
лендінг-чату.

**C2 (P0, довіра) — бот бреше про дії.** «Так, уже почала! Готую чернетку…»,
«загляньте у свій кабінет — вона має вже бути там» — генерація НЕ запущена
(її запускає тільки кнопка), «кабінету» в цьому флоу не існує. Користувач
питає «Генеруєш?» і чекає в порожнечу. Lovable-принцип: чат ВИКОНУЄ дії, а не
обіцяє їх. Роботи:
  - Системний промпт агента: пряма заборона стверджувати, що генерація
    почалась/сайт десь чекає; після підтвердження підсумку — єдина правда:
    «натисніть Створити сайт нижче» (поки кнопка) або...
  - ...краще (Lovable-режим): агент отримує сигнальний інструмент
    `start_generation`; коли користувач явно погоджується («так, генеруй»),
    агент викликає його → UI програмно тисне handleCreateSite (той самий
    auth-гейт, той самий флоу) і показує інлайн-картку прогресу (екран
    generating вже існує). «Генеруєш?» стає дією, не роллю.

**C3 — прогрес-чіпи не відповідають прийнятим фактам.** «Телефон» лишився
непозначеним, хоча бот прийняв Instagram як канал зв'язку і пішов далі.
Чіп перейменувати в «Контакт» і зараховувати телефон АБО tg/viber/IG-канал.
Чіп «Сайт буде готовий за ~3 хвилини» показувати тільки до підсумку.

**C4 — непослідовний голос.** «Знайшла у профілі», «уже почала» (жін. рід)
упереміш із нейтральним. Зафіксувати в промпті одну персону (пропозиція:
уникати роду — «мені вдалося знайти», «вже запускаю» або послідовно жіночий
як «помічниця» — рішення власника, дефолт: безродові формулювання).

**C5 — стиль повідомлень.** Довгі абзаци, повтори обіцянок «зможете
переглянути і опублікувати» тричі поспіль, емодзі в кожній репліці. Промпт:
1–3 короткі речення на репліку, одна думка, емодзі ≤1 і не в кожній репліці,
не повторювати те, що вже сказано.

**C6 — Lovable-паттерн статусів.** Інструментальні чіпи вже є (t:"tool") —
розширити: під час IG-скрапу показувати картку «Читаю профіль… знайшов N
фото, адресу» (дані вже приходять у final), під час генерації — інлайн-таймлайн
кроків (уже існує на екрані generating — переносимо в чат-стрічку як картку).

Ці пункти C1–C6 включаються у хвилі: C1 → W0 (негайний фікс до всього),
C2–C5 → W1 (промпт + сигнал start_generation), C6 → W3.

## 8. Хвилі виконання (оцінки після тех-рев'ю)

- **W0** (~0.5 дня, ПЕРШОЮ): C1 — цілісність повідомлень (репро → фікс
  persist/restore → round-trip тест). Без цього будь-який чат виглядає
  зламаним.
- **W1** (~2 дні): embedded/overlay-режим OnboardChat (рефакторинг ~6
  обгорток `100dvh`/`lg:grid`), монтування на лендінг, M3/M4/M6/M10/M11 +
  C2 (правдивість дій + сигнал start_generation) + C3/C4/C5 (чіпи, голос,
  стиль промпта).
- **W2** (~1–1.5 дні): handoff `?conv/?resume` + M1/M2/M5/M7/M8/M9/M12 +
  дефолт «Реєстрація» на /login при next→/new.
- **W3** (~0.5–1 день): аналітика, чистка CTA, C6 (Lovable-статуси в
  стрічці), should-fix'и, мобільний прогін.
- Верифікація: повний шлях root-чат → гейт → (Google-гілка І поштова гілка)
  → resume → прев'ю, два браузерні профілі (перевірка M1), мобільний в'юпорт,
  скріншоти. Обидва валідатори дали вердикт «так, після must-fix».
